=== PAGE 2 ===
1. Project context
Suwa Sarana is a community blood donation and emergency matching platform for Sri Lanka.
It is a government-related service. Public landing text mentions: 24/25 districts, 8 blood types,
"466K+ units/year" (verify that stat has a source or remove/label it).
Observed from screenshots (confirm in code):
Frontend appears to be Next.js (running at localhost:3000 ), dark theme only, with a
language switcher (English / Sinhala / Tamil) and a floating "Eligibility AI Assistant"
chatbot.
Roles seen: Donor, Admin. Other roles the owner mentions: hospital, requester, blood
bank.
Donor area: My Profile, My Matches, Notifications. Admin area: Admin Console, All
Blood Requests, Notifications, AI Triage Queue, Interactive Heatmap, Verification Portal,
flagged reports, requester verification.
Features present in some form: matching, real-time notifications, reliability score, low-
data mode, district shortage heatmap (Leaflet-style map), AI eligibility chatbot ("NBTS
grounded"), AI triage, AI poster/social post generation, Google sign-in.
Owner's stack background: NestJS, Spring Boot, Node, React, Next.js, TypeScript,
PostgreSQL; learning AWS and Docker. Keep the final deployment approach simple
enough for them to understand and maintain.
2. Final objective
A production-ready application that has:
Reliable, secure authentication (email/password and Google).
Correct role-based features and server-enforced permissions.
Accurate, natural Sinhala, Tamil and English across the entire app.
A much better AI chatbot (Sinhala, Tamil, English, Singlish) and much better AI
poster/social-post generation.
A modern, consistent, accessible UI with working light and dark themes and a balanced
colour palette.
Verified, tested behaviour across features, roles, languages, themes and devices.
A documented, repeatable AWS deployment.
3. Issues the owner already knows about
For each, find the root cause, fix it, add a regression test, and note it in the changelog.

3.1 Google authentication does not work correctly
Reproduce first. Check OAuth client ID/secret handling, redirect/callback URIs (local and
production), state /PKCE, token verification on the backend, account linking (same
email via password and Google), first-time Google users (role selection / profile
completion), session creation, error messages, and logout.
Production note: Google Console needs authorized origins and redirect URIs for the final
domain. Document the exact values.
3.2 Buttons and interactive elements
Inventory every button, link, toggle, form, menu, filter, tab, modal, and card action on
every page for every role. Verify each performs its intended action, shows
loading/success/error states, and handles failure.
Known suspicious items: the donor "Save" button, availability toggle, Low-Data Mode
toggle, "View My Matches", "Back", Admin "Refresh", "Verify User", "Open Interactive
Map", "AI Triage Queue", "Verification Portal", chatbot quick-reply chips, language
switcher, Sign out.
Produce a checklist table (page, element, expected, actual, status) in the audit.
3.3 Multilingual support (Sinhala, Tamil, English)
Switching to Sinhala or Tamil breaks parts of the app and produces unnatural or
inconsistent translations (word choice, sentence structure, context).
Required: 100% of user-facing strings are translated: UI labels, buttons, validation
messages, API error messages shown to users, empty states, toasts, emails/notifications,
chart labels, map legends, dates, numbers, pluralisation, page titles and metadata, and
chatbot UI text.
Implementation expectations: a proper i18n library (e.g. next-intl  or react-i18next ),
no hard-coded strings, translation keys organised by feature, locale persisted
(cookie/profile), lang  attribute set on <html> , proper fonts (Noto Sans Sinhala, Noto
Sans Tamil, with suitable line-height since these scripts need more vertical room),
layouts that survive longer text, ICU plural rules (this fixes issues like "1 requests").
Translation quality: use consistent medical and civic terminology (e.g. "blood donor",
"requester", "verified", "deferral", "eligibility", "district") with a glossary file ( docs/i18n-
glossary.md ) so each term is rendered the same way everywhere. Prefer natural, formal-
but-plain Sinhala/Tamil used in Sri Lankan government and health communication over
literal machine translation. Flag any term you are unsure about for human review by a
native speaker; do not silently guess. Add a script that fails CI if a key is missing in any
locale.

3.4 AI assistant chatbot
Does not always work and handles Singlish poorly. Must understand and answer in
Sinhala, Tamil, English, and Singlish (Sinhala in Latin letters, e.g. "mama blood denna
puluwanda tattoo ekak thiyenawa nam?"), and Tanglish if feasible.
Observed answer-quality bug: asked "What is the minimum age and weight to donate
blood?", it answered only the age range (18-60) and ignored weight. Verify all eligibility
facts against official Sri Lanka NBTS guidance, not model memory.
See Section 9 for the target design.
3.5 Login and registration
There are known problems; find all of them. Example seen in a screenshot: signing in
with a valid-looking account displays a generic "Validation Error" banner with no field-
level guidance. Check: validation rules and messages (localised), duplicate emails,
password policy, hashing (bcrypt/argon2), email verification, forgot/reset password flow,
rate limiting and lockout, JWT/session handling (expiry, refresh, httpOnly cookies,
CSRF), role assignment at registration (users must not be able to self-assign Admin),
logout invalidation, and redirect-after-login by role.
Test it as an attacker too (Section 8).
3.6 Role-based features and permissions are incomplete
Features for admins, hospitals, blood banks and other roles were never properly defined.
See Section 7 for a proposed matrix. Reconcile with what exists, fill gaps, and enforce on
the backend (guards/middleware, per-resource ownership checks). Hiding a button is
not security.
3.7 AI poster / social-media post generation is poor
Accuracy and visual quality are insufficient. See Section 9.2 for the target design.

5. UI/UX requirements
Use the owner's Web UI Generation Criteria Report as the reference checklist. Its key rules:
clear visual hierarchy; responsive layouts with no overflow; WCAG 2.2 AA (4.5:1 normal text,
3:1 large text and UI components); never rely on colour alone; visible focus and keyboard
access; defined hover/focus/active/disabled/loading/success/error/empty states; shared
components and design tokens; semantic tokens mapped separately for light and dark themes;
frontend role visibility is UX only, backend enforces access.
5.1 Design direction
Combine the familiarity and trust of a government service with modern UI:
Keep the good parts of government sites: clear header with identity and language
switcher, predictable navigation, plain language, prominent "Emergency / Request
blood" path, visible contact/help, a footer with policy links, breadcrumbs or Back links
where useful, high-contrast readable type, and printable/clearly structured pages for
forms.


=== PAGE 7 ===
Avoid the bad parts: dense text walls, tiny fonts, cluttered link lists, tables with no
hierarchy, dated gradients, stock-photo banners, inconsistent styles, and non-responsive
layouts.
Do not imply official government or NBTS endorsement unless the owner confirms it. No
official logos, crests or ministry names without permission.
Plain, calm tone. Medical content should read as trustworthy, not alarmist.
5.2 Colour strategy
The current UI uses red for nearly everything. Replace it with a balanced system:
Primary (actions, active navigation, links): a trustworthy blue or teal-blue.
Brand accent: a restrained blood-red/crimson used sparingly (logo, blood-type badges,
the single "Request blood / urgent" call to action).
Secondary: teal or green family for supportive elements.
Semantic only: red = error/destructive/critical shortage; amber = warning/pending;
green = success/verified; blue = info.
Neutrals: layered surfaces, borders and text greys for most of the UI.

5.3 Theme system
Light, dark, and system option, with a visible toggle, persisted per user/device, no flash of
wrong theme on load.
Semantic CSS variables / Tailwind tokens only. No hard-coded hex values in
components (grep for them and remove).
Verify every page, form, dialog, table, chart, map (tiles/legend/popups), toast, chatbot,
and focus ring in both themes. Charts and heatmap colours need separate dark/light
validation.
5.4 Components, layout and consistency
Build or consolidate a small design system: Button (primary/secondary/ghost/destructive,
sizes), Input/Select/Toggle/Checkbox, Card, Badge/Status chip (icon + text + colour),
Table, Dialog, Toast, Empty state, Skeleton/loading, Tabs, Navigation, Breadcrumb, Form
field with label/help/error.
Consistent spacing scale, type scale, radii, shadows, icon set and size.
One primary button per view. Fix the multi-colour button row in Admin.
Document it in docs/DESIGN-SYSTEM.md  (tokens, components, do/don't, accessibility
notes).
5.5 Responsive and accessible
Test at 360, 768, 1024, 1440 widths. Sidebar collapses to a drawer on mobile; tables
become cards or scroll within their container; no horizontal page scroll.
Skip-to-content link, semantic landmarks, label every input, visible focus, keyboard-
operable menus/dialogs (focus trap, Escape), ARIA only where needed, prefers-
reduced-motion , 44px minimum touch targets.
Run automated checks (axe, Lighthouse) and fix violations. Test keyboard-only and with
a screen reader at least once on key flows.
Low-data mode (existing feature): verify it works (e.g. no heavy images/maps, reduced
polling) and apply it consistently.
5.6 Feedback states
Every async action needs loading, success, error and empty states, plus double-submit
prevention. Error messages must be human, specific and localised, and must never leak stack
traces or internals.

9. AI features: target design
9.1 Eligibility chatbot
Grounded answers (RAG): build a curated, versioned knowledge base of Sri Lanka
NBTS eligibility and deferral guidance (age, weight, haemoglobin, donation intervals,
tattoos/piercings, medications, travel, illness, pregnancy, vaccinations, etc.) as structured
entries with source URL/title and a "last reviewed" date. Retrieve the relevant entries and
have the model answer only from them. Answer every part of a multi-part question (age
and weight). If the knowledge base has no answer, say so and direct the user to the
NBTS/Medical Officer. Never invent thresholds. Verify the facts with the owner or official
sources before shipping.
Languages: auto-detect Sinhala script, Tamil script, English, and Singlish/Tanglish
(romanised). Normalise romanised input (transliteration and/or a model step that
rewrites the query into standard Sinhala/English), retrieve, then reply in the user's
language (Singlish in → reply in Sinhala script or Singlish per a configurable setting,
default match the user). Include a test set of at least 100 questions across the four input
styles with expected key facts.
Safety: clear disclaimer that final eligibility is decided by the Medical Officer; no
diagnosis; recommend professional help for symptoms/emergencies; handle off-topic
and abusive messages politely; resist prompt injection.
Reliability: timeouts, retries, graceful fallback (FAQ search or friendly error) when the AI
provider fails, streaming responses if possible, conversation history limits, rate limiting,
cost monitoring.

9.2 AI poster and social media post generator
Problem: output is inaccurate and visually weak. Likely cause: asking an image model to
render text and layout. Prefer a deterministic, template-based pipeline:
1. Data from the system (blood type, units, hospital, district, date/time, contact,
campaign details) fills the poster directly, so facts are never hallucinated.
2. LLM only for copy: short headline, body and hashtags in the chosen language
(Sinhala/Tamil/English), constrained by length and tone, and validated (required
fields present, no invented phone numbers/places).
3. Render with HTML/SVG/Canvas templates (several layouts: urgent request,
donation camp, awareness, thank-you) in real fonts, correct Sinhala/Tamil shaping,
brand-consistent colours, QR code to the request/campaign page. Export PNG/PDF
at social sizes (1080×1080, 1080×1350, 1200×630, 1080×1920 story).
4. Preview and edit before export, with copy-to-clipboard captions and share links.
5. Guardrails: show an "unverified" warning or block if the requester is unverified; no
patient names/photos or sensitive details without consent; avoid scare tactics.
Add visual regression tests (screenshot comparison) for each template/language.

Prepare and document, and implement what is possible without owner credentials:

Operations: health/readiness endpoints, graceful shutdown, structured logging, basic

14. Questions to confirm with the owner (ask early, in one batch)
1. Which roles must exist at launch (donor, requester, hospital, blood bank, admin, anything
else, e.g. NBTS staff, camp organiser)? How is each verified?
2. Is the project officially affiliated with NBTS or the Ministry of Health? This decides
branding, logos and wording.
3. Which AI provider(s) and budget should be used for the chatbot and poster text? Which
API keys are available?
4. Can the owner provide authoritative NBTS eligibility documents for the knowledge
base? Who will review the Sinhala and Tamil text (a native speaker)?
5. Target domain name, AWS account/region (Sri Lanka users: consider ap-south-1
Mumbai or ap-southeast-1  Singapore for latency), and budget ceiling.
6. Map provider preference and whether a paid tile key is acceptable.
7. Email/SMS provider for notifications (SES for email; SMS gateway if needed).
8. Any compliance, hosting-location or data-retention requirements from the government
stakeholders?
